# recipi

Open-source SwiftUI recipe app for iOS (a free Mela alternative). See
README.md for the feature scope; v2 items are out of scope until v1 ships.

## Stack and conventions

- Swift 6 language mode with strict concurrency, SwiftUI, iOS 18 minimum (raise it
  only when a feature needs a newer iOS).
- MVVM with `@Observable` when a screen needs state beyond simple `@State`
  and `@Query`; plain views otherwise.
- SwiftData for storage, synced with CloudKit (private database). No backend.
- Keep the promises in `PRIVACY.md`: no network calls the person didn't
  start, no accounts, analytics or third-party dependencies.
- The Xcode project is generated by XcodeGen from `project.yml`. Edit
  `project.yml`, never the generated `.xcodeproj`, then run `xcodegen`.
- Code shared by the app and the share extension goes in
  `Packages/RecipiKit`. The `RecipiKit` target has no UI; screens go in the
  app or extension target.

## Look and feel

The `RecipiDesign` target (same package) is the design system: Notion-like
warm neutrals, system type, generous spacing, and color only where it means
something (tag colors, the paprika accent on actions, callouts).

- Use `Theme.Colors`, `Theme.Spacing`, `Theme.Radius` and `Theme.Fonts`, not
  raw colors or numbers. Every color has a light and a dark value.
- Tags get their color from `TagColor.forName(_:)`, which is stable across
  launches. Don't change its hash or palette order; that recolors tags.
- Animate with `Motion` and the helpers `withMotion(_:reduceMotion:)`,
  `.motion(_:value:)` and `.bounceEffect(value:)`, which turn movement off
  under Reduce Motion. Don't call `withAnimation` directly in screens.
- The minimum is iOS 18, so iOS 18 APIs (like the library-to-recipe zoom in
  `Recipi/Shared/ZoomTransition.swift`) need no `#available` check. Anything
  newer goes behind `#available`.

## Accessibility

`RecipiUITests/AccessibilityAuditTests.swift` runs Xcode's accessibility
audit on the main screens, at the default text size and the largest one, and
`ContrastTests` checks text colors against WCAG AA (4.5:1). Keep new screens
passing both:

- Give icon-only buttons a label, hide decorative images, and combine a row
  into one element when it reads as one thing. A row with a `Checkbox` says
  its state with `.checkedState(_:)`.
- Touch targets are at least 44 pt (`.frame(minWidth: 44, minHeight: 44)`
  with `.contentShape`); the drawn shape can stay smaller.
- Text never sits in a fixed-height frame. Custom sizes use `@ScaledMetric`,
  and side-by-side layouts stack when `dynamicTypeSize.isAccessibilitySize`.
- A text color is a `Theme.Colors` token or a `TagColor` foreground on its
  background, which the tests cover. Changing a value means rechecking them.

## SwiftData + CloudKit rules

These fail at runtime, not compile time:

- Every stored property needs a default value or must be optional.
- Every relationship must be optional and should declare an inverse.
- No `@Attribute(.unique)`. Dedupe by hand (see `Tag.findOrCreate`).
- Schema changes after release must be additive (new optional properties or
  new models only).

## Importing

`RecipeImporter` tries `SchemaRecipeParser` (JSON-LD) first, then
`FallbackRecipeParser` (microdata, WP Recipe Maker, Tasty Recipes). With no
recipe in the served HTML it follows a meta refresh or an AMP page's
canonical link, then renders the page in an offscreen `WKWebView`
(`RenderedPageReader`). Shares from Safari skip the download: the
extension's preprocessing script (`RecipiShare/Resources/SafariPage.js`)
hands over the page as Safari loaded it (`SharedPage`), and
`RecipeImporter.recipe(in:)` parses that first. When a real site fails, capture it with
`scripts/capture_fixture.py` into `Tests/RecipiKitTests/Fixtures/` and add a
row in `FixtureCorpusTests.swift` before changing the parser. Name fixtures
after the markup pattern they show. The nightly live check
(`.github/workflows/live-import-check.yml`) imports `scripts/live-check-urls.txt`.

Saving an import (`Recipe.insert(from:)`) runs `AutoTagger`: categories,
cuisines and keywords are mapped onto `TagVocabulary` (synonyms in
`TagVocabulary+Terms.swift`; a test rejects a word in two terms), traits come
from nutrition and times, and other keywords are capped. Parsers keep the
page's raw values in `RecipeDraft.tags`.

## Build and test

```sh
xcodegen
swift test --package-path Packages/RecipiKit
xcodebuild build -project Recipi.xcodeproj -scheme Recipi \
  -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO
xcodebuild test -project Recipi.xcodeproj -scheme Recipi \
  -destination 'platform=iOS Simulator,name=iPhone 16' CODE_SIGNING_ALLOWED=NO
```

`xcodebuild test` runs `RecipiTests` (hosted unit tests) and `RecipiUITests`
(a smoke test of import, scaling, cooking and groceries). Under test the app
uses an in-memory store and serves imports from the fixture pages in
`Recipi/App/TestSupport.swift`, so tests never touch iCloud or the network.
UI tests launch it with `-ui-testing`; add an `.accessibilityIdentifier` only
where a test can't find an element by its label.

CI (`.github/workflows/ci.yml`) runs on `macos-26` with the newest released
Xcode, like TestFlight. The package tests run alongside one arm64-only
`build-for-testing`, whose products go to three parallel test jobs: every
test but the audits, and the accessibility audit at each text size (a new
audit test needs its own row in that job's matrix). CodeQL runs on
`main`, weekly and on demand, not on pull requests (its Swift build takes
20+ minutes). Docs-only changes skip both.

Signing is per developer in `Config/Local.xcconfig` (gitignored). Releases are
signed with Justin's personal Apple Developer account, never a work account.

`CODE_SIGNING_ALLOWED=NO` builds compile and test, but the app they produce
has no App Group entitlement and stops at launch outside tests. To run it in
the Simulator, sign ad hoc instead: `CODE_SIGN_IDENTITY=- CODE_SIGN_STYLE=Manual
DEVELOPMENT_TEAM=`.

## TestFlight

`.github/workflows/testflight.yml` ("Run workflow" on `main`) archives Release
and uploads it to App Store Connect for the internal testers. The repo is
public, so keep it this way:

- **Only `workflow_dispatch`, only from `main`, on a GitHub-hosted Mac.**
  Never a self-hosted runner, `pull_request_target`, or a trigger a fork can
  start. No artifacts: run logs are public and symbols go to App Store Connect.
- **Secrets live in the `testflight` environment**, which needs the owner's
  approval and allows only `main`: `ASC_KEY_ID`, `ASC_ISSUER_ID` and
  `ASC_PRIVATE_KEY` (the whole `.p8`) for an App Store Connect team API key
  with the **Admin** role (cloud signing refuses App Manager keys), used by
  recipi alone. `APPLE_TEAM_ID` can be an environment variable or secret (it's
  in every signed app); the job adds it to `ci/ExportOptions-appstore.plist`.
- **Signing is cloud-managed.** The archive is unsigned,
  `scripts/ci/adhoc-sign-archive.sh` ad-hoc signs each bundle with its
  entitlements (resolving the `$(RECIPI_…)` settings) so the export keeps the
  App Group and iCloud container, then `-exportArchive` signs and uploads. A
  new extension or entitlements file means updating the script's `TARGETS`.
- **Versions:** `MARKETING_VERSION` comes from `project.yml`; bump it in a PR
  for a new App Store version. The build number is the run number
  (`<run>.<attempt>` on a re-run), and the job fails unless the app and share
  extension match.
- **CloudKit:** TestFlight builds use the production environment. Deploy the
  schema to Production in the CloudKit Console before the first upload and
  after every model change; it must stay additive from then on.
